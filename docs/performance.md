# 性能优化记录（2026-10-18）

版本说明（2026-10-19）：本文原始性能数据使用当时的 v5 阵容；默认 `baseline.toml` 现采用 v6 阵容和逐 tick 普通股息。复现下述历史场景应给 `perf_engine.py` 显式传入 `--scenario scenarios/baseline-v5.toml`，不能把阵容和支付频率变化直接当作同工作量的引擎回归。原始性能数据未改动。

最新逐 tick 改造已完成[独立性能对照](per-tick-dividends.md)：v6 人群、3000 tick、22001–22005 五种子、各三次、release、10 核共享预算、交错运行。4 线程引擎均值从 0.361 秒变为 0.388 秒（+7.6%），单线程从 0.977 秒变为 1.076 秒（+10.2%）；新程序运行旧周期规则分别为 0.360/0.994 秒。90 局计时另加 6 局预热，没有减少策略决策频率。完整方法和逐局墙钟见链接报告。

Windows 只使用可用逻辑核心的一半，向下取整、至少 1 个；Linux 没有半核限制。引擎对自动线程数和显式 `--threads N` 都应用 Windows 上限，同时不创建超过账户数的工作线程。构建、测试、多进程实验仍需自行共享机器的 CPU 预算，线程数限制不等于进程 CPU 亲和性限制。

## 本轮改动

- **Shark / Tracker 分位数**：此前每只股票、每次决策都完整排序约 600 个历史样本；现在用两次顺序统计量选择得到相同分位点，复用临时数组，从 O(n log n) 降至 O(n)。Tracker 内嵌的 Shark 同时受益。历史窗口、采样和决策频率不变。
- **Grid 价格梯级**：预计算固定的幂因子；锚点更新时仍用最新锚点计算报价，避免每次决策重复做数百次幂运算。
- **持有估值**：将新闻影响拆成各增量对剩余派息的贡献，省去临时时间线及排序。数学结果相同；一般浮点输入可能因求和顺序产生末位差异。
- **观察缓冲区**：每个工作线程复用盘口、成交、持仓及挂单数组；消息缓冲区清空后交换，每个账户仍保留独立成交游标，避免跨账户残留和重复投递。
- **盘口深度**：在挂单、撤单和部分成交时维护价位总量，读取深度时无需重新累加该价位的全部订单；价格和时间优先级保留。
- **估值热路径**：直接汇总原子标记价格，移除每次强平检查、下单和 tick 结束时的临时价格数组。

## 实测

机器：Intel Core i7-12700，20 个逻辑核心，Windows 10 19045；Rust 1.98.1，默认 release profile。Windows 上限为 10 个工作线程。

场景：`scenarios/baseline.toml`，3000 tick，10 只股票；seed 7、11、19 分别为 52、53、49 个账户。每种线程数、每个 seed 重复 3 次；旧、新二进制交替顺序、顺序执行，分别预热。下表为每组 9 局引擎耗时的中位数，含最终守恒审计，不含初始化及报告生成。

| 工作线程 | 优化前 | 优化后 | 吞吐倍数 | 耗时降低 |
|---|---:|---:|---:|---:|
| 1 | 3.0280 s | 1.0204 s | 2.97× | 66.3% |
| 4 | 0.8578 s | 0.3646 s | 2.35× | 57.5% |
| 10 | 0.4372 s | 0.2163 s | 2.02× | 50.5% |

包含进程启动、初始化及完整 CSV/HTML 报告的端到端耗时：4 线程从 0.9066 s 降至 0.4037 s；10 线程从 0.4766 s 降至 0.2626 s。

## 可以调整的设定

**优先使用 `--threads 0`。** 当前基准 TOML 保留原有 `threads = 4`，以明确历史赛制；命令行覆盖为 0 会在本机自动取 10。Linux 自动取全部可用逻辑核心，但更多线程是否有益仍应测量，撮合锁会限制扩展性。

```sh
./target/release/llm-market run scenarios/baseline.toml --threads 0 --out runs/fast-run
```

另做了 10 线程下的设置对照，每项同样为 3 个 seed × 3 次，原始记录在 `runs/perf-20261018/settings/`：

| 设置 | 中位引擎耗时 | 行为影响及判断 |
|---|---:|---|
| 当前 skew=16、每 500 tick 审计 | 0.2116 s | 对照 |
| `max_tick_skew = 128` | 0.2137 s | 本次没有加速；允许快账户领先更多，会改变相对交易机会。暂不建议为性能放宽。 |
| `check_interval = 0` | 0.2071 s | 仅快约 2%，区间重叠；只在结束时检查守恒，故障定位更晚。保留当前默认。 |

**决策间隔由 bot 自己设置。** 系统性能优化应减少提供同等服务的成本，不把降低 bot 决策频率作为优化方向。

批量实验还可测试**多局并行、每局减少线程**：Windows 下所有比赛需共享半核预算。多线程争用和相对时序仍会影响结果，需单独测吞吐，不以单局延迟推断；本轮尚未测出这一方式的收益。

## 追加：锁和编译器优化

在上述版本基础上继续做了两项锁优化：

- **合并调度临界区**：完成上一项任务后，直接在同一个锁保护范围内领取下一项；正常、不等待的路径每个账户 tick 的调度锁获取从 2 次降到 1 次。bot 执行前仍释放调度锁，原有 skew、暂停审计和异常处理规则保留。
- **盘口改为读写锁**：观察和采样持读锁，允许多个 bot 同时读取同一股票；下单、撮合和撤单持写锁。不会复用过期盘口快照。

第一项独立对照中，10 线程耗时中位数从 0.2155 s 降至 0.2080 s（约 3.5%）；再加入盘口读写锁的独立对照从 0.2131 s 降至 0.2047 s（约 4%）。不同批次不可直接累加百分比，以下四版本交替对照用于衡量合计收益。

同时试验了编译器生成代码的优化：普通 release 启用 `lto = "thin"` 和 `codegen-units = 1`；本机专用构建额外使用 `-C target-cpu=native`。后者让编译器按当前 CPU 的指令能力和调度特点优化，并未加入手写汇编。普通 release 保持原来的目标指令集兼容范围。

环境和场景与前一轮相同；每版每个线程档为 3 个 seed × 5 次，四个版本交替顺序执行。表中为引擎耗时中位数：

| 版本 | 4 线程 | 10 线程 | 10 线程相对上轮耗时降低 |
|---|---:|---:|---:|
| 上轮优化完成的版本 | 0.3477 s | 0.2141 s | — |
| 仅追加两项锁优化 | 0.3490 s | 0.2031 s | 5.2% |
| 锁优化 + ThinLTO / 单 codegen unit | 0.3412 s | 0.1981 s | 7.5% |
| 再启用本机 CPU 优化 | 0.2896 s | 0.1744 s | 18.6% |

锁优化在 4 线程下基本持平，在 10 线程下更有价值。4 线程启用本机 CPU 优化后，相对上轮减少约 16.7% 耗时。原始记录：`runs/perf-locks-20261018/codegen/comparison.json`，包含冻结二进制哈希及全部报告。120 局正式测量完成守恒审计，无 bot 异常、禁用或跳过决策。新增覆盖慢 bot、skew=1、频繁审计及线程退出的调度回归测试，工作区现在共 54 个测试。

最终构建的普通版、本机专用版分别在 seed 7、11、19 做了单线程对照；6 组的成交、K 线、盘口和新闻 CSV 逐字节一致，剔除计时及超预算计数后的摘要一致。记录保存在 `runs/perf-locks-20261018/validation/validation.json`。普通构建的 `--threads 0` 仍实测为 10 线程。

使用：

```sh
# 普通 release：包括锁优化、ThinLTO，输出 target/release/
python tools/build_release.py
# 本机 CPU 专用：输出 target/native/release/，不会覆盖普通产物
python tools/build_release.py --native
./target/native/release/llm-market run scenarios/baseline.toml --threads 0 --out runs/native-run
```

Windows 构建脚本同时限制 Cargo 并发数及构建进程/子进程的 CPU 亲和性，LLVM 和链接器也共享半核预算；Linux 不添加此限制。本机 CPU 专用二进制只应在兼容 CPU 上运行。ThinLTO 增加编译成本，实验中切换配置后仅 CLI 的构建约需 30 秒。

手写汇编仍应以具体热点为前提：先检查生成代码，再比较指令内建函数、SIMD 或手写实现。等待锁、指针追踪和分支密集的撮合流程无法单靠更短的算术指令解决；本轮没有证据表明手写汇编会比已测出的方案更有收益。

## 后续方向：所有 bot 可复用的公共结果

以下是提交 `92717b5` 时的候选方向；公共派息、盘口缓存、标记价格及调度中位数的落地情况见下文“第二轮”。其余候选仍需测量后取舍。基准 seed 7 的 52 个账户、3000 tick、10 只股票会产生 156,000 次决策、1,560,000 次单只股票观察构造；该提交虽已复用数组，仍要逐次访问盘口树和查询派息。

1. **按股票变更版本缓存公共快照。** `engine.rs::observation` 每次都调用 `depth_into` 遍历盘口前 N 档。可以缓存前 N 档、最新成交价、标记价格及成交序号，盘口没变就复用。缓存按实际订单/成交变更失效，不能只按 tick 缓存：异步执行下，同一 tick 的 bot 可能看到不同盘口，不能引入全局 tick 同步。第一步可保留现有 API，复制缓存的连续数组；进一步共享不可变快照才需要调整 bot API。发布快照的分配和引用计数也有成本，应先测读写比例与命中率。派息依账户个人 tick 查询，不宜直接塞进同一个版本缓存。
2. **预计算公共时间查询。** 世界在开局已生成，但 `world.rs::dividend` 仍在每个账户、每只股票、每次观察时二分查询。可预先生成按 tick 索引的派息表，或按事件区间缓存；10 只股票 × 3000 tick 的 i64 表约 234 KiB。派息期数、费用周期边界、已到期提示数量等公共时间结果也可复用；最终公开新闻的正文可只构造一次。内部预计算必须按账户自己的 tick 和披露权限取值，不能提前把未来数据交给 bot；私有新闻区间仍按账户生成。
3. **公共成交统计一次维护、多方查询。** 在成交记录中维护累计成交量、成交额、主动买卖量，按成交序号做前缀和。bot 请求某段公开成交区间时，用两端相减得到同一统计结果，避免各自重复扫描。必须保留账户成交游标和 `trade_tape_limit` 的范围。不同 bot 的窗口、采样时点和私有信息不同，不能直接共享任意策略信号。异步成交的 tick 可能乱序，公共统计应明确采用追加序号还是个人 tick 的窗口定义，不能混用；只维护确有使用者的指标。

价位总挂单量和标记价格本来就是全 bot 共享的结果，本轮已将前者改成增量维护。下一轮优先试验公共时间表和盘口快照缓存，属于减少重复计算，不改变 bot 的决策间隔。

## 后续方向：撮合、调度、结算与报告

| 方向 | 当前开销与改法 | 需要验证的边界 |
|---|---|---|
| 标记价格增量更新 | `book.rs::record` 每笔成交遍历全部滚动窗口桶；维护有效成交额、成交量总和，过期时扣减，争取从 O(窗口长度) 降到摊销 O(1)，同时缩短盘口写锁持有时间。 | 个人 tick 乱序、旧 tick 与新 tick 的桶冲突、跨越整个窗口、空窗口；不能假定成交 tick 单调递增。默认窗口仅 20，收益需实测。 |

| 批量消息和撤单 | 同一输入订单产生的成交逐笔锁 maker 邮箱、更新 treasury 原子量；可合并同一收件人的锁获取及已按逐笔规则计算的费用，复用邮箱缓冲。同一股票的批量撤单可共用一次写锁。 | 不能合并成交额后重新取整费用；消息必须在当前任务结束前发布。批量投递/撤单会改变其他 bot 能插入执行的位置，需明确这种时序变化，并比较更长的单次持锁时间。 |
| 调度数据结构和唤醒 | 每个账户 tick 更新 Fenwick 树、扫描运行任务，并调用 `notify_all`；可优化完成 tick 的计数结构和等待者唤醒。 | 保留准确的 reference tick、skew、审计暂停和退出条件；先测争用及无效唤醒，避免盲目改成自旋或无锁队列。 |

建议实施顺序：先做公共时间查询和快照缓存的对照，再做标记价格增量更新、订单索引及同价撮合。邮箱批量化和调度重构涉及更大的并发时序变化，应结合锁等待测量单独验证。所有方向都保留 bot 自己决定何时更新信号和下单的权利。

## 第二轮：公共计算与调度优化（2026-10-18）

这轮只修改 `market` 引擎，bot 代码、决策间隔、信息披露、撮合优先级、skew 和审计设置均保持原有规则。

- **公共派息表**：开局按股票和 tick 预计算，所有账户复用同一份只读结果，查询仍用各自的个人 tick。基准表为 240,000 字节；总表超过 8 MiB 或查询超出表范围时，回退到原始时间线二分查询，避免长局产生无界的额外内存。预计算表不通过 bot API 暴露。
- **公共盘口前缀**：挂单、撤单和部分成交时同步维护配置深度的买卖盘连续数组；读取直接复制，撮合最优价也复用数组首项。删除价位只补充新的末档，读取更多档位时仍遍历原始盘口。缓存由现有股票写锁保护，反映每一次实际修改，不按 tick 延迟刷新，也不增加读侧锁或引用计数。
- **增量标记价格**：维护有效窗口内的成交额和数量，只处理过期桶及受影响的槽位，省去每笔成交扫描整个窗口。保留原实现对迟到成交、环形桶碰撞及空窗口的处理，窗口较大时收益更明显。
- **增量调度中位数**：账户完成进度每次只增加 1，中位数只会前进。用直接计数和当前中位位置替代 Fenwick 树的两次更新及一次查询；整局中位位置最多前进 `ticks` 次。reference tick 仍是所有账户（含已完成账户）的精确下中位数，没有用近似值放宽调度规则。

测试扩展到 58 项，包含逐笔均价与原始全扫描算法对照、缓存深度与完整挂单汇总对照、派息重复时间点及越界回退、调度中位数与账户进度完整排序对照。原有慢 bot、频繁审计、退出和消息投递检查继续通过；Clippy 无警告。

### 第二轮实测

仍在同一台 i7-12700 Windows 机器上，最多 10 个工作线程；旧版为提交 `92717b5` 的普通 release，新版使用相同的 ThinLTO / 单 codegen unit 配置，均不启用 native 指令选项。对照顺序交替、每个二进制预热，所有构建和比赛串行进行。

默认 `baseline.toml`，seed 7、11、19，每个线程档每版重复 5 次，表为各 15 局引擎耗时中位数：

| 工作线程 | 上一版 | 第二轮最终版 | 耗时降低 |
|---|---:|---:|---:|
| 1 | 0.9744 s | 0.9581 s | 1.7% |
| 4 | 0.3416 s | 0.3320 s | 2.8% |
| 10 | 0.1971 s | 0.1921 s | 2.6% |

同批端到端中位耗时：4 线程从 0.3864 s 降至 0.3739 s，10 线程从 0.2311 s 降至 0.2262 s。默认场景增益较小，运行区间仍有重叠，不能把单次快慢当作保证。

## 第三轮：数据局部性与缓存一致性（2026-10-18）

以 `c8155e6` 为基线，针对内存访问方式做了三项实验，保留两项：

- **账户挂单采用紧凑数组。** `OrderStore` 将递增订单 ID 与订单内容分开连续存储。二分查找只读取 ID；`live_orders`、`own_touch` 及观察构造顺序扫描紧凑内容，不再扫描哈希桶。正常下单追加到末尾，删除时移动尾部；迭代天然按 ID 排序，观察构造省去一次排序。默认上限只有 40 个有效挂单，适合这种布局。这里同时减少了哈希和排序开销，不能将全部收益归因于 CPU 缓存。
- **共享标记价只在变化时发布。** 原来每次有效下单都写共享原子价格，包括未成交或价格未变化的情况。现在比较盘口修改前后的标记价，只在变化时写入，减少反复写相同数值带来的缓存一致性流量。发布放在股票写锁内，还避免了原来“旧线程解锁后，覆盖另一个线程已发布的新价格”的竞态。
- **撤回邮箱缓存行隔离。** 曾将各邮箱锁及队列头按 64 字节对齐；同批对照中，1 / 4 / 10 线程中位耗时相对未填充版本分别变化 +1.4% / -0.1% / +1.4%，没有足够收益支持保留。最终代码没有这个额外布局。

没有改动 bot 决策间隔、撮合 FIFO、skew 或审计设置。原先全撤回报使用哈希遍历顺序，没有顺序保证；现在按订单 ID 排列。`open_orders` 原本就按 ID 排列，因此其可见顺序不变。释放股份时仍按原来的 tick / ID 从新到旧撤单。共享价格发布竞态修复可能改变多线程的估值时序，单线程对照保持一致。

同一台 Windows 机器，最多 10 个工作线程，普通 release，seed 7、11、19，交替顺序、串行运行。默认场景每版每档 3 个 seed × 5 次，以下为各 15 局引擎耗时中位数：

| 4 | 0.3392 s | 0.3219 s | 5.1% |

同批端到端中位耗时，4 线程从 0.3749 s 降至 0.3565 s，10 线程从 0.2373 s 降至 0.2314 s。单独“按需发布价格”的早期对照收益较小；上表是两项改动的合计，不与前两轮不同批次的百分比直接累加。

### 接下来值得测试的方向

| 优先方向 | 结合当前代码的具体改法 | 取舍与验证重点 |
