# Swift 在 v21 的退化诊断

本轮只研究原因，不修改生产 Swift、市场规则或默认场景。复用已审查的 Swift 与 debug-run 的只读 Probe；Probe 每次将重建订单与真实订单逐项比较，不提交自己的订单。记录会改变多线程时序，因此新增 trace 是独立比赛，不是 v21 原始比赛回放。

1. 分析已有 v21 开发 48 局与独立 40 局：两个 Swift 账户逐局收益、盈亏分布、现金收益恒等式、成交方向/对手、买入后盘口变化。以世界为独立单位，两次重复先合并，不把所有成交当独立样本。
2. 新增只读记录：90601–90604，control / both 各一局，共 8 局，两种 Swift 都记录。分类进场、补仓、减仓、信号清仓与终局清仓；检查盘口缺边、点差、成交量门槛、深度/动量的分数贡献、请求与成交量、成交后 10/30/100 ticks 的报价变化。前瞻报价是事后诊断，并非可以保证成交的收益；不回灌未来信息。
3. 独立参数消融：90701–90706，各两次，control、both、both-no-depth、both-no-momentum、both-standard-single，共 60 局。后两种信号消融分别把两个 Swift 的既有 depth 或 momentum 参数置零；single 只把 standard 的 single_entry 置一，其余参数/资金不变，early-single 保持原样。用于检验假说，不据此宣布优化版本，也不挑最佳参数部署。

具体问题：费用是否解释损失；替换 Coral 和 Value 的影响是否相同；盘口买量优势是否因卖盘缺失而失真；价格变化信号是否更不稳定；standard 的连续调仓是否放大问题。消融会改变成交、仓位和其他账户的反应，不能视为固定市场上的纯信号贡献。

所有新增比赛 release、4 个市场线程，Windows 10 核总亲和性预算，arena_gate 串行；方案顺序轮换。冻结源代码、二进制与配置哈希，逐局核对初始资产、终局抽签、新闻世界一致，检查 20 次守恒审计和 bot 错误/跳过/禁用。不同实验子组不能直接比较绝对收益。
