# Swift 交易调查台

## v9 新增：远期消息与风险时间线

- “消息与交易关联”按新闻 ID 合并首次收报和后续区间更新，区分普通消息与 `forecast` 远期研究，列出公开、生效、实际提前量和同期买卖。点击可查看从收报到生效后 100 ticks 的成交与强平。窗口可能重叠，这不是策略交易动机的因果归因。
- “收报到生效连线”将已收到消息和其生效时点叠在 K 线与原有进出场连线上；截至游标模式不会使用游标之后的区间更新、成交或强平来填这些关联行。
- “强平与坏账”显示触发前后现金、市值、实际卖出额、费用与核销金额；图上方块标记可打开该次实际强平成交明细。旧录制无此字段时保持空白。案例见 [强平核对](liquidation-audit.md)。
- 长局允许只录制关注账户，其他 bot 照常参赛：`--record swift,horizon,titan`，也可以填逗号分隔的精确账户名。顶栏分别显示录制数和实际参赛数。默认仍录制全部账户。

```text
python tools/swift_debugger.py run --scenario runs/v9-research/configs/h1000.toml --out runs/v9-replay --seed 29001 --threads 4 --record swift,horizon,titan
python tools/swift_debugger.py serve --run runs/v9-replay --port 8769 --open
```

下面列出的 8765–8768 样例是历史录制，不会自动变成 v9。新录制会改变并发时序，不能冒充普通性能实验中的逐笔行情。

这是本地、离线的赛后逐 tick 调试器。它录制一场新的真实比赛，展示全部账户的交易和状态，并为 Swift 重建信号与执行条件。标准版保留原加减仓行为；当前 v6 的较早进退版启用单次入场模式。没有给 Swift 增加新闻、估值或对手身份等输入。

**当前基准已用 NewsV2 替换旧 News。** 本页现有 `runs/swift-cashflows-seed7`（8768）及更早录制均生成于替换之前，仍展示其实际旧 News 阵容，不能自动变成新比赛。现在执行默认 `run` 命令会使用新阵容；新录制应另选目录，保留旧证据。NewsV2 的成交、持仓、现金流和新闻可按通用账户查看；Swift 专用信号重建器只用于 `swift`，不会把 NewsV2 冒充为纯 Swift。

## 启动

在仓库根目录运行（需要 Rust 和 Python，无需 Node、npm 或网络 CDN）：

```sh
python tools/swift_debugger.py run --out runs/my-investigation --seed 7 --threads 4
python tools/swift_debugger.py serve --run runs/my-investigation --open
```

第一步在必要时自动构建 release，然后录制、核对并压缩数据。输出目录必须尚不存在，避免覆盖研究记录。第二步只监听 `127.0.0.1:8765`，关闭服务不会删除数据；下次直接运行第二条命令即可。端口冲突时加 `--port 8766`。Windows 构建和运行共用半核 CPU 预算，录制经过项目基准锁。

最新样例位于 `runs/swift-cashflows-seed7`，包含 146 个账户、3000 ticks，采用 0.6% 闲置费与逐 tick 组合收益；`swift-early-single` 现金为 2,000 元，每只股票初始 2 股，`swift-standard` 资金不变。此前 `runs/swift-small-dense-seed7` 是相同扩容与资金配置、旧费用及组合周期，可用端口 8767 查看。更早的 `runs/swift-single-entry-seed7` 保留 54 个账户及未缩小资金的 single，端口 8766；`runs/swift-debug-seed7-final` 保留两个均可加减仓的 Swift 和用户指出的 T1 交易，端口 8765。这些旧录制没有被新比赛覆盖，页面顶栏按数据实际规则显示费用和组合周期。

```sh
python tools/swift_debugger.py serve --run runs/swift-cashflows-seed7 --port 8768 --open
```

其他选项：`run --scenario scenarios/其他场景.toml`、`--ticks N`、`--challenge news_v2`、`--build` 强制重建。挑战者默认现金 20,000 元、每股初始 20 股、策略默认参数。更细的资金和参数配置直接写入一个新场景，再用 `--scenario` 选择。只运行已经审查的 bot。

已有录制可用 `python tools/swift_debugger.py pack --run runs/my-investigation` 重新生成前端数据。旧比赛只有 K 线 / 全市场成交 CSV，没有 bot 当时的观察，不能补造为完整决策回放。

## 建议的调查顺序

1. 选 `swift-standard`，在“标的拆分”中找净价差最差或分红最多的股票。
2. 打开默认的“整轮操作”，选择“亏损优先”。默认排除含开局库存的轮次；取消勾选可纳入。
3. 点击一行或图中连线，K 线缩放到这一轮。圆圈是入场、方块是出场，整轮端点用加权均价；红线是扣交易费后价差盈利、绿线是亏损，零价差为灰色。通过“整轮明细”查看每笔买卖和逐笔仓位，用“上一轮 / 下一轮”连续调查。“展开本轮 FIFO 连线”可拆看加减仓配对。
4. 在“成交记录”点开原始买卖点，比较下单目标、实际成交量和最优报价。信号允许买入，不代表一定买得到：价差、可用预算、已有订单和动作额度都可能阻止执行。
5. 用“消息与现金流”切换新闻 / 股息收入，检查新闻收到、新闻公开、股息实际生效三个时点。Swift 收到了这些消息，但原策略不读取新闻内容。
6. 选择对比账户，将另一只 Swift、Coral 或交易对手的买卖点叠加到同一行情中。“交易对手”页可点击账户直接加入对比。
7. 导出筛选后的 CSV，或者导出包含来源哈希、规则、参数与当前决策输入的 JSON，保留具体证据。

## 页面内容

- 全部账户可搜索、按最终收益率 / 最大标记回撤 / 成交次数排序。只按需加载主选和对比账户。
- 1 / 5 / 10 / 30 / 50 tick K 线；成交量、当时观察到的买一卖一、买卖成交点、新闻收报点。
- Swift 总信号、10 / 30 tick 主动成交方向、盘口不平衡、加权动量；入场 / 退出门槛、实际持股和目标股数。点击图例可隐藏曲线。
- 滚轮缩放、拖动平移、联动十字线、全局视图、点击图表定位；播放 / 暂停、单 tick 前后、上一笔 / 下一笔成交、输入精确 tick。快捷键：左右箭头、空格、`[` / `]`，输入框及按钮聚焦时保留其原生行为。
- 决策快照显示动作前后现金和持仓、观察报价和成交方向、Swift 的目标与执行条件。Swift 保存实际观察的十档盘口及逐笔成交批次，其他 bot 保存精简盘口和实际动作；不虚构其他策略的内部理由。
- 权益图包含标记权益、现金、累计普通分红、交易及库存残差、累计费用；对比账户显示权益收益率，期末结算权益单独标出。
- 成交表保留 maker / taker、订单 ID、交易费、撮合 tick 和收到回报的 tick。FIFO 配对显示部分成交、交易费后价差及持有期间的事后有利 / 不利价格变化。初始库存单独标记。
- 全部账户均支持整轮统计：按每只股票从空仓到持仓再到空仓分组；加仓和部分退出都属于同一轮。显示加权买卖均价、买卖股数、订单数、费用、最大持仓及组成成交。未平仓轮次保留记录，但不画虚构的退出连线。
- 图上可切换整轮 / FIFO / 关闭连线，聚焦一轮或显示全部，开局库存用虚线并默认隐藏。缩放跨过一端时保留可见线段。净价差颜色不包含分红，不是账户总收益；整轮均价端点也不是新增的实际成交点。
- 股息、组合收益、利息、闲置费、终值提示、消息、拒单、订单回报及原始 JSON 可查。股票拆分、交易对手汇总、账本误差和策略参数可导出。

## 统计口径与信息边界

**回放不是重新交易。** 引擎观察器只记录数据，不生成订单；Swift 的重建器输出不参与撮合，而是与真实动作逐项比较。若发生任何动作不一致，打包失败，页面核对区也会显示异常。修改 Swift 源码后，应同步维护诊断重建器。

**三种时间分开。** 图上的成交点按撮合 tick 放置；成交表另列账户收到回报的 tick。主动成交可以定位自己的下单 tick；被动成交不能把撮合 tick 当成挂单时刻。账户个人时钟不同，不能把同 tick 的所有账户理解为同时看到同一个盘口。

**全市场 K 线是事后信息。** 它可能包含 bot 决策之后才发生的同 tick 成交。分析决策依据应看快照中的实际盘口和实际观察批次。聚合 K 线中的信号 / 仓位取该桶最后一条账户记录，精确解释请用 1 tick 或快照。“图表截至游标”只截断图表，账户排名和数据表仍是整局分析；这不是隐藏未来信息的盲测模式。全局新闻真值须显式勾选。交易对手身份只来自赛后成交日志，Swift 下单时看不到。

**只对收到的成交记账一次。** `post_fills` 是动作后即时回报预览；下一次决策输入里的 `fills` 才是策略收到的同一笔回报。分析器只计后者，并在期末归集最终邮箱，避免漏掉最后一笔被动成交或重复计算收入。

**整轮不是策略自报意图。** 以账户收报顺序的库存归零切分，同一批回报中先清仓再买入也拆成两轮。跨时钟的被动成交不强行按全局撮合 tick 重排。整轮加权入价包含这一轮全部买入（以及可能存在的开局库存成本），加权出价包含全部卖出；这条线用于总结，不表示单次可执行的交易。库存销毁或来源不明时标为调整，整轮净价差留空；未平仓也不假定按最后价格已卖出。

**单次入场模式。** `swift-early-single` 的 `single_entry=1` 只改仓位执行：零成交可重试，任意正成交后不再加仓、不随权益微调，信号退出后持续清仓，即使途中买盘恢复也不能补仓，完全空仓后才重启。每只股票独立，不禁止同时持有不同股票；初始库存计作已有持仓。一次 IOC 可撮合多笔，卖出也可能分多 tick，因此“单次入场”不等于只有两条成交记录。快照会明确显示不补仓和持续清仓原因。

**盈亏不混在一起。** FIFO 价差已扣两端成交费，不分配普通分红、组合收益、利息和闲置费。初始股票用开局价格作成本，不算交易入场。闲置费销毁的股票是库存调整，不冒充卖出；账本分别记录闲置费的现金与股票价值部分。

权益图中的交易及库存残差为：

`标记权益 − 初始权益 − 普通分红 − 组合收益 + 成交费 + 闲置费 + 利息`

它包含库存市值变化，也可能包含坏账核销等影响，不能直接叫“已实现炒价差利润”。最终排名以现金加现金流终值结算，与图中股票标记市值不是同一个口径。曲线和最大回撤使用每个 tick 末的标记权益；不是 tick 内逐笔最大回撤。

**未来价格评估是事后指标。** 后 10 / 30 / 100 tick 变化从收到回报起算，使用未来实际观察中间价（单边盘口退回最新成交价）；保留原始价格涨跌方向，卖出不翻转。没有未来观察则留空，不填零，也不假定该价格可成交。持有期间最大有利 / 不利变化同样使用观察价格。

金额原始单位是分，图表显示元。股息及新闻变化需要再除以 `dividend_scale`；当前为 50，故整数股息单位是 1/50 分。组合规则的整数费率独立除以 `combo_scale`（旧数据缺省为 1，当前为 50）。普通分红按单股整仓、组合按每条规则完整套数，每 tick 四舍五入到分，沿用个人时钟结算设计。负组合对称取整并计入对账；新闻公开不等于派息额已改变。收入事件里的 amount 已是到账的分，不能再除以 scale。

### 单次入场与进出场连线追加验证

release、seed 7、4 线程、3000 ticks，Windows 共用 10 核预算，录制 1 次。新样例 54 个账户对账通过；两个 Swift 共 6000 次决策与重建器完全一致，均零跳过。单次入场版共有 89 轮实际买入操作，每轮成交买单数最多为 1，持仓期间再次提交买单的次数为 0；标准版保留补仓行为。本次 91 项 Rust 测试、严格 Clippy 和 20 项 Python 测试通过。

录制（含等待基准锁及进程启动）2.517 秒，离线打包 81.092 秒；这里只是该次录制开销，不是引擎性能前后比较。模式增加的是每股持仓状态判断，不改引擎、线程数或决策间隔。单次入场会显著减少补足仓位的机会：这一条路径标准版最终 +44.55%，较早进退单次入场版 −3.63%，两者原本信号参数也不同，不能当作单因素收益实验，更不能宣称新模式收益更高。

原样例 T1 的 50→87、1 股、−0.35 元是 FIFO 的一个片段。新统计将 50→89 的完整持仓过程合并成一轮：买卖各 7 股，4 个买单、3 个卖单，扣全部成交费后净价差 **−3.07 元**，未计分红。两份录制均重新核对整轮与 FIFO 收益、成交归属和期末库存；证据见 [追加验证 JSON](swift-single-entry-validation.json)。

### 单次入场版为何亏损：对已录制路径的拆账

|---|---:|
| 实际买入后退出的 89 轮净价差（已扣交易费） | +1,671.25 |
| 开局自带股票卖出的净价差（已扣交易费） | −804.46 |
| 普通分红 | +790.34 |
| 组合分红 | +17.85 |
| 闲置费 | −3,047.39 |
| 最终损益 | **−1,372.41** |

所有买卖合计净价差 +866.79 元，费用前后没有重复扣成交费。初始权益 37,842 元，平均持仓市值仅 1,089.64 元；逐 tick 的持仓市值 / 权益比值平均 2.886%。首个买单请求数量中位数 124 股、实际成交中位数 8 股，首单成交完成比例中位数约 6.96%。该模式只要第一单成交正数就锁定本轮仓位，因而放弃了后续补足目标数量的机会，交易额与分红规模都明显缩小。

该历史录制的闲置费按每 50 tick 的平均账户权益乘 0.2% 计算（当前新比赛已为 0.6%），并用该期符合条件的成交额乘 1% 抵扣，不是只针对现金余额收费，也不是简单少持股就免除；抵扣按期生效。这局低成交额版本未能靠交易和分红覆盖费用。这个分解解释的是既有路径的最终亏损，不等同于“改掉闲置费后重新比赛会赚这么多”的反事实结果。

实现还同时禁止了按权益微调减仓，并把退出锁定为持续清仓；这超出了单独关闭加仓的对照范围。该局未出现被禁止的权益再平衡减仓，退出锁定在买盘恢复时额外触发 1 个观察（T1 tick 1450，当时剩 2 股）。不能用标准版 +44.55% 与此版 −3.63% 直接量化“加仓”的单独贡献：它们信号参数本来不同，多线程市场路径也受交易行为影响。交付时仅检查零补仓与对账不足以评价策略，必须同时报告成交完成度、资金使用率与费用拆分。

本机 20 逻辑核，所有运行限制在 10 核内，release 构建，实验串行。结果摘要保存在 [debugger-validation.json](debugger-validation.json)，原始输出位于 `runs/debugger-validation`。

## 文件与实现

- `trace/account-N.jsonl`：每个个人 tick 一行，另加期末归集行。包括实际输入、动作、预览回报、状态、统计和 Swift 诊断。
- `trace-manifest.json`：账户身份、开局公开规则、参数、结果、重建核对；`market/` 保留常规报告与 CSV。
- `data/manifest.json`、`market.json.gz`、`account-N.json.gz`：前端压缩数据；缺少精确现金闲置费拆分的早期录制会拒绝打包，需重新录制。
- `command.json`、`source-scenario.toml`：当前启动器记录命令、构建文件 / 二进制 / Swift 哈希、录制及打包时间和源场景。参数覆盖在命令中，实际生效规则在 trace manifest 中。最初制作的 seed 7 样例早于完整 provenance 增补，具体记录以其文件实际内容为准。
- `crates/cli/src/bin/debug-run.rs` 与 `crates/cli/src/debug/swift.rs`：录制及 Swift 诊断；`tools/debugger_data.py`：对账和 FIFO；`tools/swift_debugger.py`：启动、打包和仅本地服务。
- `tools/debugger_episodes.py`：整轮库存归组；`tools/debugger/trade-links.js`：进出场连接。采用 ECharts [自定义系列与 weakFilter 缩放](https://github.com/apache/echarts-doc/blob/master/en/tutorial/custom-series.md)，避免每笔配对各创建一个 series。前端数据 schema 升至 2，旧录制需重新 pack。
- 前端采用本地 vendored Apache ECharts 5.6.0（Apache-2.0），官方 npm 包校验信息和许可证在 `tools/debugger/vendor/`。选择它是因为 K 线、成交散点、多个信号坐标轴与缩放可以共用同一 tick 轴；用 ResizeObserver 跟随侧栏和窗口变化。参考官方[尺寸管理](https://echarts.apache.org/handbook/en/concepts/chart-size/)与[事件文档](https://echarts.apache.org/handbook/en/concepts/event/)。
